HumVisual 1.0.0 · skill paper

One prompt for the words and the page

Two agent skills did separate jobs. One rewrote prose that sounded generated. The other turned terminal output into HTML pages. This paper describes the merge, shows what each half catches that the other misses, and gives the measurements behind the result.

merged from Humanizer 3.1.0 merged from visual-explainer 0.11.0 26 prose patterns 38 files, plus this page 1 October 2026

Abstract. HumVisual is a single agent skill with two entry jobs and one set of evidence rules. The prose job rewrites text so it reads like the writer who meant it, without changing what it says. The visual job builds self-contained HTML pages for systems, diffs, plans, data, and decks. A request that needs both runs the prose pass first, because page copy written before the prose pass keeps the tells the prose rules exist to remove. The merged package holds 49,723 words across 38 files, of which 4,517 words load on every use and the rest load on demand. This page is the 39th file.

01

Two jobs behind one prompt

The routing table is the first thing the merged prompt does with a request. It decides which job runs, and it decides that before any HTML or any edit.

Routing, as written in SKILL.md
The request Job Where the output goes
“Humanize this”, a draft, a commit message, a pull request body Prose The chat, or the named file
A diagram, an architecture, a diff review, a plan review, a recap, a table, a deck Visual ~/.agent/diagrams/<name>.html, opened in a browser
A page that needs words on it Both, prose first Page copy written to the prose rules
Ask for AI-readable output or a source brief Both <name>.md beside <name>.html
Prose job

Rewrite the text

Marks 26 tells, drafts a rewrite that keeps every supported claim, then checks the draft against the source before writing the final version.

  • Catches staging, rule-bound rhythm, inflated significance, chat residue
  • Returns a draft, the patterns still present, and the final text
  • In file mode touches prose only, and leaves code, paths, and frontmatter alone
Visual job

Build the page

Picks a representation that fits the content, plans a palette and type roles before writing HTML, and runs a delivery checklist before the file ships.

  • Catches the terminal dump, the unlabelled arrow, the generic dark violet template
  • Returns one complete HTML document plus a short chat summary
  • Uses Mermaid for connected flows, tables for matrices, cards for architecture

What the rewrite kept

The specific detail carries the writer's voice, so it survives every pattern check: the file named final_v7.docx, comments that stay pinned to their sentence while the text around them changes, and the price. Removing tells is half the job. A rewrite that also strips the human fingerprints has failed at the second half.

Read the two panels together and the division of labour is plain. The prose job fixes the sentence. The visual job fixes the medium, and it also fixes the words a page carries, because a button that says “Submit” when it writes a file is the same defect wearing a different costume.

03

Why the prose half needs a reason, not a list

A language model writes whatever is most likely to come next, so by default it makes the choice that fits the widest range of readers and subjects. A person writes for one reader and one subject, so their choices are uneven and specific. Every one of the 26 patterns is a form of that default choice: staging that adds weight instead of a fact, rhythm and formatting applied by rule, ordinary facts dressed as turning points, leftovers from the chat, and replies that re-explain context the reader already has.

The reason matters more than the list, because word habits change with every model release while structural habits persist. A skill that only banned words would rot. A skill that explains the default can be updated with one line per release.

The bar for acting

A tell counts in proportion to how rarely a careful writer would make it on purpose. Patterns 1 to 5 justify an edit on one sighting. Anything marked weak alone needs company from other tells in the same passage first.

The six strongest patterns, with the group they belong to

04

One evidence bar, two jobs

The merge rests on a single rule that both halves already enforced. Every fact, name, number, date, quote, citation, and code reference comes from the source, the user, or a command that was actually run. A gap gets a question or a shorter sentence, never a plausible guess.

05

The visual rules, and how this page follows them

The visual half plans before it writes. This page's plan is four named values, a type pair, and one sentence of layout: a letterpress memo on cool chalk, a 68ch measure of serif in a wide field, a contents rail on the left, and the data set in ruled tables. The rules below are the ones that changed the output, and each one is visible somewhere on this page.

Palette

Light values sit on :root, and the dark scheme redefines tokens only. Components are styled through tokens, so the media query never touches a component rule. Neutrals carry a trace of the indigo accent rather than sitting at pure mid-grey. The ruled ground behind the text uses one more token, a low-alpha version of the ink, so the page gains texture without adding a hue.

The invariants that shaped this page

Structure and access
  • Semantic elements throughout: real <table>, <figure>, <figcaption>, <details>, heading order from one to three
  • The figure carries role="img" and an aria-label on the shell, not on the SVG
  • Wide tables sit in a scroll container, and every grid child sets min-width: 0
  • Focus rings on links, the disclosure control, and every scroll target
Rhetoric and restraint
  • One claim per figure, stated in the caption, with the mechanism drawn rather than named
  • Every arrow in the flow diagram carries a label
  • Depth used twice: the hero rule and the elevated table frames. The rest is flat or recessed
  • No motion beyond hover states, and none of it under prefers-reduced-motion
One deliberate omission

No Mermaid. The diagram above is hand-written SVG so the page stays self-contained with no network dependency beyond the two web fonts, and so the arrows carry the exact labels the caption claims. The skill still routes connected flows to Mermaid, where zoom, pan, and expand earn their keep on a diagram with fifteen nodes rather than five.

06

What the merge changed

Merging two packages means choosing one layout and one version story. The pattern numbers stayed put, because every section reference in both prompts depends on them, and the optional utilities kept their upstream names so host configurations keep working.

Decisions, with the reason each one was made
Decision Before After Reason
Skill location plugins/visual-explainer/SKILL.md SKILL.md at the root One folder loads in every agent, and every ./references/ path resolves from the root
Prose patterns inline in Humanizer's SKILL.md references/prose-patterns.md Progressive disclosure: the index loads always, the watch lists and examples load on the first rewrite
Pattern numbering 1 to 26 1 to 26 Unchanged, so every § reference in both prompts still resolves
Utility names visual_explainer, visual-explainer-mcp, visual-explainer-pptx unchanged Renaming would break MCP host configs and Pi installs for no gain
Project config visual-explainer.config.md humvisual.config.md The file seeds the page palette and font pair, so it carries the skill's name
Prose entry point Description trigger only /humanize plus the seven visual commands One command shape for both halves
Version story 3.1.0 and 0.11.0 1.0.0 across six files The validator fails on any drift between the prompt, the changelog, and the manifests
The validator is the merge's regression test

scripts/validate-package.py runs with the standard library alone. It checks the version in six places, one root SKILL.md, pattern numbering in the reference, pattern names in the README table, section reference targets in the prompt and the commands, the 5,500 word budget, the absence of em dashes in the prompt, every file the prompt routes to, command frontmatter, the package binaries, and both upstream copyrights. Nine of these checks were verified by breaking each one on a scratch copy.

08

Install and use

There is no build step. The skill is Markdown, and the only hard requirement for the visual half is a browser. 

# Claude Code, as a marketplace plugin
/plugin marketplace add <owner>/humvisual
/plugin install humvisual@humvisual

# Any agent with the Skills CLI
npx skills add ./HumVisual --global --agent '*'

# Any agent with a skills folder: copy the folder in and read SKILL.md
cp -r ./HumVisual ~/.config/opencode/skill/humvisual

Asking for either job

Humanize this: [paste text]
Humanize the prose in docs/launch-post.md
Draw a diagram of our authentication flow
Review this diff on this branch as a page
Turn this plan into slides

Add --quick to /generate-web-diagram, /diff-review, /plan-review, or /project-recap and the agent emits a compact JSON spec instead of hand-written HTML. The bundled renderer validates the spec and writes the page. Visual output lands in ~/.agent/diagrams/ and opens in a browser.
